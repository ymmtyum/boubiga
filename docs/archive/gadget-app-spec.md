- 2026-05-18 時点で、SwiftUI のローカルプロトタイプとして 5 タブ構成は実装済み。
- 現在は `SwiftData` や `Supabase` 永続化は未接続で、`AppModels.swift` のサンプルデータとローカルテンプレートで体験検証を進めている。
- `マイギア` は、一覧表示、詳細表示、追加シート、テンプレート選択付き登録フローまで実装済み。
- 商品テンプレートは、`iphone_sku.json` による iPhone 群、人気カメラ / PC のコード定義テンプレート、ユーザー本人の実機材テンプレートを併用している。
- 初回登録では `購入価格` と `現在価値` は必須ではない。まず登録し、後から詳細を詰める方針で進める。

## 1. コンセプト

**「ガジェットを通じて自分を知り、知らない誰かを助けるアプリ」**

買わせるツールではなく、出会わせるツール。所有しているガジェットを登録することで、以下の3つの価値が同時に生まれる。

1. **個人の資産管理**：何を持っているか忘れない。眠り資産の流動化。

2. **自己理解**：購買傾向・満足度から自分の消費観を可視化。

3. **集合知の貢献**：登録データが匿名化され、初心者向け診断の素材になる。

詳しい人の登録という行為そのものが、初心者への情報提供になる構造。明示的なレビュー投稿を求めない。

## 3. 各タブの内容

### 3.1 マイギア

所有しているガジェットの一覧。

**確定要素**

- 商品マスタから選んで登録（マスタにないものは申請）
- 追加画面は 2 ステップ構成にする
- 追加画面の先頭に `手動で入力する` 導線を置く
- テンプレート候補をタイル形式で表示する
- 初期テンプレートの大枠は `iPhone / カメラ / PC`
- `iPhone` は `iphone_sku.json` をベースに構成する
- ユーザー本人の実機材テンプレートを優先表示する
- 現状の登録済み実機材テンプレート:
  `MacBook Pro M1 Pro / iPhone 16 Pro / DJI Mic 2 / DJI OSMO Pocket 3 / Apple Studio Display / BOOX Go 7 / α7S 初代`
- 画像は当面ローカル同梱で扱う
- 購入価格と現在価値は初回登録で必須にしない
- 各ガジェットにステータスバッジ
- 後継機あり
- 長期未使用
- 保証残り僅か
- メルカリ相場上昇中
- バッジ起点で診断・売却フローへ誘導
- 一覧は棚っぽい 2 カラムカード表示を基本にする
- 詳細画面から購入情報・満足度・次アクションが見えるようにする

**余白**

- 並び順のデフォルト（購入日順／カテゴリ順／満足度順）
- フィルタ項目（カテゴリ、使用頻度、満足度など）
- リスト表示／グリッド表示の切替の有無
- 1アイテムの表示要素（サムネ、商品名、購入日、満足度、価格、それ以上は？）
- 売却済みアイテムをここに表示するか／別画面か
- テンプレート数が増えた際の検索・絞り込み UI
- カメラ / PC も JSON や外部マスタ化するか

### 3.2 遍歴

購入・売却・レビューの時系列ビュー。

**確定要素**

- タイムライン形式（カレンダーではない）
- 購入・売却・満足度記録の3種類のイベント
- 現在のプロトタイプでは読み物的な時系列一覧を先行実装する

**余白**

- イベントの粒度（日／月／年単位での集約）
- ガジェット遍歴を「ガジェット観の物語」として読ませる演出をどこまでやるか
- 年間サマリーの自動生成（「今年買ったガジェット◯個、手放した◯個、純増◯円」など）

### 3.3 探す

カテゴリブラウズと診断の入り口。

**確定要素**

- 初心者向け診断：プロファイル質問 → 似たユーザーが満足度高く使っているガジェットを提示
- 上級者向けディグ：カテゴリブラウズで他ユーザーの使用統計を見る
- 「おすすめ」ではなく「実際に使われている統計」として提示
- 診断結果は権威の声ではなく、似たプロファイルの実データ
- 現在のプロトタイプでは診断の入口とカテゴリ統計の入口を先に置く

**余白**

- 診断質問の設計（何を聞く？ 何問？）
- プロファイルマッチングのロジック（初期はルールベースか、Claude APIで解釈か）
- カテゴリ階層の設計（大分類のみ／中分類まで）
- 「他ユーザー」を匿名化する粒度（個人特定リスクの管理）
- 集合知が育つまでの初期データをどう準備するか（Yumaさん自身のデータ、運営シード）

### 3.4 分析

グラフ重視。所有データから性格までを可視化。

**確定要素**

- 累計支出（月／年）
- カテゴリ別所有内訳
- 満足度の高い／低いカテゴリ
- 衝動買い率（ウィッシュ経由 vs 即購入）
- 眠り資産の総額（メルカリ相場ベース）
- 売却での回収金額
- **性格分析**：所有物から読み取れるユーザータイプ
- 例：ミニマル志向／実験家／型番マニア／世代追従型 など
- Claude APIで月次・四半期レポート生成
- 現在のプロトタイプでは Charts ベースの可視化を先行する

**余白**

- 性格タイプの定義（軸を何にする？ いくつ用意する？）
- 性格分析の更新頻度（リアルタイム／週次／月次）
- 無料／Pro機能の境界
- グラフの種類（円・棒・折れ線の使い分け）

### 3.5 設定

**確定要素**

- 通知設定（プッシュON/OFF、タイミング、時刻）
- 通貨設定
- 解約済み／売却済みの履歴アクセス
- 商品申請フォーム
- Proアップグレード
- 現在のプロトタイプでは通知設定、商品申請導線、Pro 導線を先行実装する

**余白**

- Proの価格設計（買い切りか月額か、サブスクBoxは買い切り¥1,200／月¥300）
- 無料の上限（登録件数？）
- データエクスポート機能（JSON、CSV）

## 4. 商品マスタ運用（確定）

- 商品マスタは運営側で手作業整備
- マスタにない商品はユーザーが**製品名のテキストのみ**で申請
- 運営が調べて登録
- 登録完了時に申請者に通知
- 申請者には初回登録権を付与（小さなご褒美）
- 重複申請防止のため、申請前に類似検索
- 初期プロトタイプでは、本番マスタの代わりにローカルテンプレート群で UX を検証する

**余白**

- 申請から登録までのSLA目安（24h以内？ 数日？）
- カテゴリ初期整備の範囲（全カテゴリか、特定カテゴリから始めるか）
- 同一商品のバリエーション扱い（色違い、容量違い）

## 5. メルカリ相場連携（確定）

- 初期は「相場を見る」ボタンでメルカリ検索URLを開くだけ
- 自動相場取得・スクレイピングは利用規約リスクのため後回し
- ユーザー数が見えてから判断

**余白**

- 将来的にヤフオクAPIなど代替手段を検討するか
- 「長期未使用」判定の閾値（3ヶ月？ 6ヶ月？）

## 6. 購買機能（確定）

- アプリ内での購買フローは作らない
- アフィリエイトリンクなどの収益化は検討対象から外す
- 「欲しい」気持ちは**ウィッシュリスト経由**ではなく**探すタブのディグ体験**で吸収

**余白**

- ウィッシュリスト機能を完全に削るか、一部残すか
- 「クールダウン通知」など購入抑制機能の扱い

## 7. 技術スタック

### 確定

- iOS：SwiftUI
- バックエンド：Supabase（Postgres + Auth + Storage）
- AI機能：Claude API（性格分析、月次レポート）
- 通知：APNs + Supabase Edge Functions

### 現在の実装前提

- 現在のアプリ本体は SwiftUI のみで動作している
- データ保持はローカルのサンプルモデルで代替している
- 画像はアプリ bundle に同梱したローカルファイルを参照している
- `iphone_sku.json` をアプリ bundle に含め、iPhone テンプレート読込元として使っている

### 余白

- Web版（Expo/Next.js）を視野に入れるか、iOS専用で行くか
- 商品マスタの管理画面をどう作るか（Supabase Studio直編集／専用管理画面）
- 画像保存（Supabase Storage、容量上限、CDN）
- 商品メタデータ取得の自動化（バーコード／型番検索）の優先度

## 8. データモデル（概略）

```
products（商品マスタ：運営管理）
  id, name, category, brand, release_date, image_url, successor_id

ownerships（ユーザーの所有関係）
  id, user_id, product_id, purchased_at, purchase_price, purchase_reason,
  sold_at, sold_price, status (active/sold/disposed)

reviews（満足度の時系列記録）
  id, ownership_id, recorded_at, score, note, usage_frequency

product_requests（商品申請）
  id, user_id, raw_text, status, fulfilled_product_id, requested_at

  user_id, profile_type, generated_at, raw_analysis
```

- 「これと組み合わせて使っている」リンクのテーブル設計

## 10. MVPスコープ（要検討）

**初期リリースは、まず個人ツールとして成立する体験を優先する。**

検討候補：

- マイギアの登録と詳細更新を先に完成させる
- 遍歴の追加・編集を入れて個人ログとして成立させる
- 探す / 分析 / 設定はプロトタイプを維持しつつ段階的に本実装へ近づける
- 集合知や AI 分析は、個人データ体験が安定してから接続する

**余白**：MVP範囲の最終決定

## 11. 設計上の論点メモ

過去の対話から残っている課題：

- **鶏卵問題**：初心者診断には上級者データが必要。上級者は個人ツールとしての価値で集める必要がある
- **SALIDAとのリソース分散**：自己理解ツールとして近接。棲み分けか統合か未決
- **publishing paralysisリスク**：他人のレビュー参照型ではなく、内省型に振る方がYumaさんに合う
- **「詳しい人」の継続インセンティブ**：貢献の可視化が必要かもしれない
